# AerisVault UI: Software Architecture & Feature Specification

> **Status:** The core UI is **implemented** (database management, single analysis, comparison, settings). Features marked below that depend on DynaPrep (simulation setup wizard) or are listed under future work (3D kinematics, report generation, user authentication) are **not yet implemented**.

## 1. Executive Summary
**AerisVault UI** is the interactive, web-based frontend application of the AerisVault SPDM (Simulation Process and Data Management) ecosystem.

Built on top of the Streamlit framework, it serves as the central command portal for engineers working with LS-DYNA parachute simulations. AerisVault UI strictly adheres to the "Thin UI" paradigm: it performs zero heavy engineering computations. Instead, it acts as an intelligent orchestrator — collecting user inputs, managing the database, and delegating the post-processing workload to the `dynaprocessing` library.

## 2. Software Architecture
The application is structured to ensure maximum reusability, secure state management, and a clean separation between visual elements and data transactions.

### 2.1. Structural Layers
* **`pages/` (The Application Views):** Implements the Streamlit multipage architecture. Each file (e.g., `01_New_Simulation.py`, `02_Results_Analysis.py`) represents an isolated workspace or tool within the portal.
* **`ui/` (Reusable Components):** A library of visual "Lego blocks" specific to AerisVault. This includes standardized Plotly chart templates, branded data tables, and custom form selectors (e.g., a "Mesh Selector" dropdown linked to the database).
* **`core/` (Backend Logic):** The underlying nervous system of the web app. It handles secure connections to the SQLite metadata database (via SQLAlchemy) and manages the complex `st.session_state` to ensure user inputs persist seamlessly across page navigations.

### 2.2. Dependencies
As an application, AerisVault UI glues together external web frameworks and internal computational engines:
* **`streamlit`**: The core web framework for rendering the reactive Python UI.
* **`sqlalchemy`**: The ORM (Object Relational Mapper) used to interact with the local SQLite metadata database.
* **Internal Libraries (`dynaprep`, `dynaprocessing`)**: Installed via the monorepo workspace to handle file generation and mathematical analysis.

## 3. Core Features & Capabilities (Functional Requirements)

### 3.1. Simulation Setup Wizard (Integration with DynaPrep)
* **Feature:** A user-friendly form interface to configure complex FSI drop tests.
* **Behavior:** The UI provides intuitive inputs (dropdowns for parachutes and materials, sliders for drop altitude, numeric fields for payload mass). Upon submission, it validates the inputs and passes them to `dynaprep.generator` to silently assemble the LS-DYNA input decks in the background.

### 3.2. Job Tracking & Metadata Database
* **Feature:** A persistent catalog of all simulations and available assets.
* **Capabilities:**
  * **Mesh Library:** Queries the database to show users only valid, pre-approved CSD/CFD meshes.
  * **Simulation History:** A dashboard displaying past simulation runs, their parameters, execution status (Pending, Running, Completed), and the user who initiated them.

### 3.3. Interactive Visualization (Integration with DynaProcessing)
* **Feature:** Browser-based rendering of FSI physics without requiring local software installations.
* **Capabilities:**
  * **2D Telemetry:** Fetches filtered `Curve` objects from `dynaprocessing` and renders them as highly interactive Plotly graphs (zoom, pan, hover tooltips) for G-force, velocity, and aerodynamic coefficients.
  * **3D Kinematics:** Loads lightweight `.parquet` files generated by the post-processor to display the 3D deployment sequence and canopy inflation directly in the web browser.

### 3.4. Session & State Management
* **Feature:** Persistent user context.
* **Behavior:** The application utilizes Streamlit's `session_state` to "remember" which simulation a user is currently analyzing. If a user filters a G-force graph on the "Analysis" page and navigates to the "Reporting" page, their selected dataset remains active without needing to be reloaded from the disk.

### 3.5. Automated Report Generation
* **Feature:** One-click engineering sign-off reports.
* **Behavior:** Allows users to compile selected graphs, metadata, and 3D snapshots into a standardized, branded PDF report for sharing with stakeholders or storing in a QMS (Quality Management System).

## 4. Non-Functional Requirements (NFRs)

### 4.1. The "Thin UI" Principle (Performance)
* The UI must remain highly responsive. All heavy data parsing, file writing, or digital signal processing must be delegated to the internal libraries. Streamlit's `@st.cache_data` and `@st.cache_resource` decorators must be utilized to prevent redundant recalculations when the user interacts with UI widgets.

### 4.2. Security & Access Control
* **Data Isolation:** The application must never expose raw LS-DYNA `.k` mesh files containing proprietary canopy geometries directly to the web client for download. Only aggregated results and lightweight visualizations are transmitted to the browser.
* **SQL Injection Protection:** All database queries must be routed through the SQLAlchemy ORM; raw SQL strings are prohibited to prevent malicious user inputs.

### 4.3. Deployment Readiness
* The application must be fully containerizable. It must rely on environment variables (e.g., `DATABASE_URL`, `SOLVER_PATH`) rather than hardcoded local paths, ensuring it can be effortlessly deployed via Docker to a cloud server or a local intranet environment.
